# KAY Sentinel SSZ Serialization & Merkleization Profile (`SSZ-V1`)

> **Status:** Sections 1–4 are the normative encoding rules and are stable.
> Section 5's worked example is generated by
> [`scripts/ssz_reference.py`](../scripts/ssz_reference.py) against the real
> vectors in the fixtures repo's `validation_vectors/`, using
> [`remerkleable`](https://pypi.org/project/remerkleable/) — an existing,
> independently-maintained SSZ implementation, not a from-scratch
> reimplementation. It replaces an earlier hand-written walkthrough that
> undercounted the total serialized length by 4 bytes (see §5.3). This still
> validates the encoding/merkleization layer only — no Geth/Reth extractor
> exists yet, so nothing here has been checked against a real client trace.

## 1. Introduction & Normative References

Unless explicitly overridden by this profile, all serialization and
`hash_tree_root` behavior SHALL conform to the Ethereum SimpleSerialize
(SSZ) specification. The `expected_root_hash` in any Layer 2 verification
manifest is defined as `hash_tree_root(SemanticStateRecord)`.

Any modification to this schema (field reordering, type changes,
addition/removal of fields, or changes to capacity bounds) SHALL invalidate
this profile and MUST NOT reuse the `SSZ-V1` identifier — define a new
profile string (e.g. `SSZ-V2`) instead.

## 2. Type Schema & Structural Bounds

```python
MAX_STORAGE_UPDATES = 65536  # 2^16
MAX_ACCOUNTS        = 16384  # 2^14

class StorageUpdate(Container):
    slot: Bytes32
    original: Bytes32
    current: Bytes32

class AccountDelta(Container):
    address: Bytes20
    original_nonce: uint64
    current_nonce: uint64
    original_balance: uint256
    current_balance: uint256
    original_code_hash: Bytes32
    current_code_hash: Bytes32
    storage_updates: List[StorageUpdate, MAX_STORAGE_UPDATES]

class SemanticStateRecord(Container):
    consensus_outcome: uint8     # 0 = Included, 1 = Rejected
    execution_outcome: uint8     # 0 = Success, 1 = Revert, 2 = ExceptionalHalt
    account_deltas: List[AccountDelta, MAX_ACCOUNTS]
```

Implementations MUST reject inputs exceeding these declared limits.

## 3. Serialized Byte-Level Packing

Layer 1's byte-wise lexicographical sorting is immutable and MUST be
preserved exactly by the serializer.

### 3.1 Integer Endianness

All `uint64` and `uint256` values MUST be serialized as unsigned
little-endian integers, regardless of internal representation in the host
client.

### 3.2 `AccountDelta` Fixed/Variable Layout

`AccountDelta` is variable-size (it contains `storage_updates`, a list). Its
fixed segment is:

```
address(20) + original_nonce(8) + current_nonce(8) + original_balance(32)
  + current_balance(32) + original_code_hash(32) + current_code_hash(32)
  + storage_updates_offset(4, uint32 LE)
= 168 bytes
```

`storage_updates_offset` MUST equal 168 (the fixed segment's own length) —
i.e. it always points to the byte immediately following itself, since the
variable segment (the actual `StorageUpdate` entries, 96 bytes each) starts
right there.

### 3.3 `account_deltas` List Layout — the part the original draft missed

`account_deltas` is a `List[AccountDelta, ...]` and `AccountDelta` is itself
variable-size. Per the SSZ list-of-variable-size-elements rule, the list
serializes as: **one 4-byte offset per element** (an offset table), followed
by the concatenated serialized elements — the same pattern a variable-size
container uses for one variable field, just repeated per list element.

For a list with N elements, this is `4*N` bytes of offset table, not the
implicit 0 bytes an earlier draft of this profile assumed. This is why the
top-level record's real total is 4 bytes larger than a walkthrough that
only counts the header, the container's own offset field, and the
container payload.

## 4. Canonical Merkleization (`hash_tree_root`)

### 4.1 32-Byte Leaf Chunking

- `Bytes20` (address): padded to 32 bytes with trailing zeros.
- `uint64` (nonces): 8-byte little-endian, padded to 32 bytes with trailing
  zeros.
- `uint256` & `Bytes32`: occupy one 32-byte chunk natively, no padding.

### 4.2 Container Hashing

`hash_tree_root` of a container = recursively compute each field's tree
root in declared order, then pair them up a binary Merkle tree.
`AccountDelta` has exactly 8 fields (a clean power of two, depth-3 tree, no
padding needed):

```
[R_addr, R_orig_nonce, R_curr_nonce, R_orig_bal, R_curr_bal,
 R_orig_code, R_curr_code, R_storage_list]
```

### 4.3 List Merkleization & Length Mixing

For `storage_updates` and `account_deltas`:

1. Gather `hash_tree_root` of each active element.
2. Merkleize over the full declared limit (2^16 / 2^14 respectively), using
   SSZ default (zero) nodes to fill unallocated positions.
3. Apply `mix_in_length` with the active element count as a little-endian
   `uint256`.

## 5. Worked Example — `KS-ST-001` (real, reproducible)

Generated by running:

```bash
pip install -r scripts/requirements.txt
python scripts/ssz_reference.py path/to/kaysentinel-fixtures/validation_vectors/KS-ST-001.json
```

`KS-ST-001` has one account (`0x1000...0001`), nonce 5→6, balance
`1000000000000000000` → `999999999999950000`, no code (both code hashes
equal `EMPTY_CODE_HASH`), and zero surviving storage updates (the
identity-loop was pruned).

### 5.1 Real serialized length: **178 bytes**, not 174

The breakdown:

| Segment | Bytes |
|---|---|
| `SemanticStateRecord` fixed header (`consensus_outcome` + `execution_outcome` + `account_deltas` offset) | 6 |
| `account_deltas` list offset table (1 element → 1 offset entry) | 4 |
| `AccountDelta` payload (fixed segment incl. its own offset field; `storage_updates` contributes 0 bytes since it's empty) | 168 |
| **Total** | **178** |

An earlier draft of this profile computed `2 + 4 + 168 = 174`, omitting the
4-byte list offset table in row 2 — that's the gap. §3.3 above documents the
general rule so this doesn't recur for vectors with more accounts.
